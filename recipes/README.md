# The recipes

A recipe is a procedure you run when someone asks for one, or at a milestone `WGM.md` lists as a standing review, as [conventions/verification.md](../conventions/verification.md) describes. Nothing that runs often (a hook, a schedule, a pipeline) starts one, because a recipe takes minutes and often several readers.

## Choosing one

Go down the list, cheapest first, and take the first recipe that answers the request. Its report names any part of the request it did not answer. A request to build or fix that also asks for a recipe gets both, in the order the work needs.

- To build or fix something: no recipe. The standard applies.
- What the session taught, for the project's own instructions and tools: [`learning-from-a-session.md`](learning-from-a-session.md).
- A vague request about the tree as it stands ("review this", "what do you think"): [`reading-it-cold.md`](reading-it-cold.md).
- Whether a document as it stands lets its reader act: [`reviewing-documentation.md`](reviewing-documentation.md).
- A choice between versions of a text, a rule or a design: [`choosing-between-versions.md`](choosing-between-versions.md).
- Writing or rewriting the text a product's users read (labels, messages, help, what a screen reader says), in one language or several: [`writing-text-user-sees.md`](writing-text-user-sees.md).
- A change to judge (a diff, a branch, a document or plan being changed): [`reviewing-a-change.md`](reviewing-a-change.md).
- Making a plan, or working out how something people will use should work, before anything is built: [`making-a-plan.md`](making-a-plan.md).
- A review of the whole tree for unnecessary complexity: [`reviewing-the-mechanisms.md`](reviewing-the-mechanisms.md).

A request no recipe here answers is answered without one, under the standard.

Each recipe opens with a frontmatter block, for assistants that load the whole tree as skills. This section still says which recipe a request goes to.

## What the recipes share

You brief each investigator, verify what they find and, where the recipe ends in a revision, apply the fixes. An **investigator**, a person or an assistant session started for it, is a separate reader that knows only its brief, and is said to have fresh context.

**Investigators** work against the tree under review and edit nothing in it, and nobody changes that tree while they read, so that every finding points at text that is still there when it is verified. Running the product and working on copies in a scratch directory are not edits. They run the product only on an instance whose data nobody needs, or on a copy of the data kept in a place where that data is allowed to be kept, because a review that writes to data people use can lose it. Where the only instance holds data people use, they only read it, and a finding that needs a write there is reported unverified. They delete or change only what they created, found by the identifiers they noted, never by a pattern such as a name prefix, because a pattern also matches what someone else created. Where there are several, they work in parallel, each with fresh context and none seeing the others' findings, and a finding two of them reach independently is more likely real. Each brief asks the investigator to keep what they showed apart from what they inferred, and to say where they looked when a search found nothing, because a reader takes an inference not kept apart, or a search that found nothing reported without where they looked, for something shown.

**You verify** every finding against the repository, and a finding that rests on a measurement by making the measurement again, and hand this check to nobody, because investigators are often wrong and another reader can be wrong in the same way. A finding weighs as much as the item of the order that the finding harms, as [the standard](../STANDARD.md#the-order) says. A violation of the repository's own rules harms the item the rule serves. Severity is judged against the deployment the project actually has, because a trade-off that is fine in a trusted, self-hosted setting is not a vulnerability, and the report names the deployment it assumed.

**The time of whoever asked** is the scarcest in a run, because the run can do many things at once and they answer one question at a time. So, while whoever asked is there, the run first looks around and asks whatever would change its work, in as few batches as it can. Then it works to the end. It sets aside each question that comes up and does everything that does not depend on it, and it stops early only when nothing is left that can be done without an answer, as at each vote in [`choosing-between-versions.md`](choosing-between-versions.md). At the end it puts the questions together in one message, numbered. Each question comes with its recommendation and says what it asks and what each answer would change, so that whoever asked can answer it without opening the change or reading back through the conversation. For a text, the question also shows the passage as it reads now, in place. Each question keeps its number, in later messages too, until the questions are answered.

**What reaches whoever asked is checked.** A text proposed has each claim checked wherever a check is possible, and is shown in place, with the sentences around it, because a sentence that reads well alone can be wrong beside its neighbors. A fact told, such as a count, a diagnosis or "done", is checked against the thing it describes, not against a log or a report that says so, and where the thing cannot be reached, the run says what the fact rests on.

**A fix changes only what its finding names**. For a finding about a fact, what the finding names is every place in what the run reviews that states the fact. Moving text, or widening what a sentence covers, is a finding of its own, because a fix that reaches past its finding is where the next defect most often comes from. A fix to how a text is written changes how it says something, never what, beyond cutting what the reader does not use. Its facts, numbers, names, commands, paths, quotations, the strength of each obligation, the position it takes and any structure an outside authority sets for it stay. Where the fix would need a fact the text lacks, or a change to that structure, or the text reads two ways, the fix is a question, never a guess. Before the fixed text is shown or applied, it is compared with the text it replaces, item by item, and checked for added facts. Correcting what a text says, such as a wrong command, is a finding of its own. A finding in what someone else answers for is reported, as [the standard](../STANDARD.md#the-order) says, goes into the brief of each later full round, and does not keep the rounds going.

**A run that may outlast its session writes as it goes**: the plan holds the goal, the decisions that constrain it, the steps and the checks, and a log beside it, or on its own where there is no plan, holds each question set aside, each finding declined with its reason, and the state of the work, each written before the run acts on it, so that the next session goes on from what is written. A brief carries the plan and the log's open questions and declined findings, so that no round raises them again, except where a recipe limits what its investigators see.

**In a public repository**, a finding that carries a secret or a way in, and the report, question or declined finding that holds it, are kept in the private place `WGM.md` names, or with whoever asked. They are never kept anywhere the public can read, such as the backlog, a plan or its log, the specification or a frozen analysis. This holds whichever recipe found the finding and even where `WGM.md` names a public place for findings, because they are each a way in until the finding is fixed. A plan or its log records only that they are kept privately. In any repository, a credential that may still work is reported to whoever asked, to be revoked, because removing it from the text leaves it in the history.

**The run decides by itself**, and sets a question aside where [the standard](../STANDARD.md#the-order) says to ask, where the request itself seems wrong, where a step needs a decision it cannot find written, where a finding it cannot verify would be expensive to undo, or where it cannot tell what is true or what was asked, such as how to start the product or which of two readings an answer means.

**The local facts** a run needs are in `WGM.md` where there is one, and otherwise inferred from the repository, saying which. A copy of wgm that a repository uses and does not write, wherever it is kept or linked, is not part of what a run reviews. A problem found in it is given to whoever asked to report as an issue on wgm, stated without the repository's names, code or data, because the issue is public.
